# 공개 문서 문체 규칙

저장소가 공개라서 README·기획서·릴리스 노트를 누구나 읽는다. 읽는 사람이 "AI가 찍어낸 글"이라고 느끼면 내용까지 믿지 않게 된다. 이 규칙은 Wikipedia "Signs of AI writing"과 한국어 윤문 자료(im-not-ai의 패턴 분류 등)에서 추린 것이고, 2026-11 README를 고칠 때 처음 적용했다.

원칙은 세 가지다.
1. 사실, 수치, 고유명사, 버전, 명령어는 바꾸지 않는다. 문체를 고치다 정확도를 잃으면 안 된다.
2. 막연한 말을 구체적인 동작·조건·결과로 바꾼다.
3. 서식은 내용이 필요로 할 때만 쓴다.

## 1. 서식

- **"굵은 소제목 — 설명" 목록을 쓰지 않는다.** AI 글의 가장 뚜렷한 표시다. 항목이 많으면 소제목(`###`)으로 나누고 그 아래를 문장으로 쓴다. 짧은 참고 목록은 `이름: 설명` 정도로 충분하다.
- 줄표(—)를 쓰지 않는다. 쉼표, 콜론, 괄호, 또는 문장을 나눠서 쓴다.
- 굵은 글씨는 한 화면에 한두 번, 정말 놓치면 안 되는 경고에만 쓴다. 문서 첫 줄 소개 문장을 굵게 하지 않는다.
- 이모지로 목록·제목을 꾸미지 않는다. 앱 버튼 기호(`✎` 등)처럼 실제 화면에 있는 것은 괜찮다.
- 항목 수를 셋, 다섯으로 맞추려고 채우거나 줄이지 않는다. 작은 항목으로 목록을 부풀리지 않는다.
- 표는 형식별 지원 범위처럼 칸이 실제로 비교될 때만 쓴다.

## 2. 어휘

- 부풀린 말을 쓰지 않는다: "강력한", "혁신적인", "완벽한", "매끄러운", "손쉽게", "출시", "정식 출시", "첫 …". 이 앱은 스토어에 올리지 않고 GitHub Releases로만 나눈다.
- 상투구를 쓰지 않는다: "결론적으로", "주목할 만하다", "핵심적인 요소", "~라고 볼 수 있다", "~하고자 합니다".
- 번역투를 우리말 서술어로 바꾼다.
  - "~를 통해 ~할 수 있습니다" → "~로 ~합니다"
  - "~에 의해 생성된" → "~가 만든"
  - "~에 있어서" → "~에서", "~할 때"
  - 이중 피동 "~되어집니다" → "~됩니다"
- 형식명사("것", "점", "수", "바")가 한 문장에 여러 번 나오면 줄인다.
- 완곡 표현을 겹치지 않는다: "~할 수 있을 것으로 보입니다" → "~합니다" 또는 "~할 수 있습니다". 정말 불확실하면 무엇이 불확실한지 조건을 적는다 ("Android 11에서는 안 됩니다").
- 한 대상은 한 이름으로 부른다. 같은 것을 "쪽/페이지/면"처럼 번갈아 부르지 않는다. 앱 안 용어(탭, 그룹, 파일 묶음, 필기)를 기획서와 같게 쓴다.
- 우리말로 쓸 수 있는 영어는 우리말로 쓰고, 영어를 괄호로 덧붙이는 일도 꼭 필요할 때만 한다.

## 3. 문장

- "A가 아니라 B입니다", "단순히 A가 아니라 B까지" 같은 대비 구문을 쓰지 않는다. B만 말한다.
- 문두 접속사("또한", "따라서", "즉", "이를 통해")가 이어지지 않게 한다. 대부분 지워도 뜻이 통한다.
- 문장 길이와 끝맺음을 섞는다. 모든 문장이 "~합니다."로 같은 길이면 기계적으로 읽힌다. 다만 짧은 문장만 늘어놓는 것도 또 다른 획일이다.
- 글 끝에 요약·감탄·권유("지금 바로 써 보세요!")를 붙이지 않는다.
- 효과를 말하지 말고 동작을 말한다.
  - 나쁨: "형식과 상관없이 같은 화면"
  - 좋음: "어떤 형식이든 세로로 이어지는 페이지로 보여 줍니다."
  - 나쁨: "확대 상태를 배려한 똑똑한 스와이프"
  - 좋음: "확대한 상태에서는 페이지 끝에 닿은 뒤 한 번 더 밀어야 넘어가므로, 확대한 쪽을 둘러보다가 탭이 바뀌지는 않습니다."
- 한계는 솔직하고 구체적으로 적는다: "docx는 Word와 같은 자리에서 줄과 쪽이 바뀌도록 맞췄고, 다른 형식은 원본과 조금 다를 수 있습니다. 차트, 수식, SmartArt는 자리만 표시합니다."

## 4. 내용이 맞는지

문체보다 먼저 내용이 지금 코드와 맞아야 한다. 고치는 김에 확인한다.
- 버전, 지원 Android 버전, 배포 방법(GitHub Releases, 1.0.0부터 정식 릴리스), 앱 식별자
- 라이브러리 목록은 `app/build.gradle.kts`, 구조는 CLAUDE.md의 코드 구조와 맞는지
- 사실을 모르면 지어내지 않는다. 만든 사람의 동기("~하려고 만들었습니다")처럼 확인할 수 없는 말은 쓰지 않는다.

## 5. 문서별 메모

- **README**: 첫 문단은 무엇을 하는 앱인지 한두 문장으로 말하고, 다음 문단은 어떤 상황에서 쓸모 있는지 예를 든다. 배지·스크린샷·형식 표는 유지한다.
- **릴리스 노트**: 주요 변경만 적는다. 1.0.0 전의 사전 출시는 "개발 버전입니다. 기능과 저장 형식은 바뀔 수 있습니다."로 시작했다. 끝에 APK와 서명 인증서의 SHA-256을 적는다(CLAUDE.md 빌드 절). 사용자가 직접 고친 이전 릴리스 노트(`gh release view <태그>`)를 본보기로 삼는다.
- **앱 안 문구**: 이 스킬이 아니라 `ui-copy-ko` 스킬을 따른다. 화면 문구는 쉬운 말보다 전문 용어로 통일한다(용어 목록이 거기 있다). 문서에서 화면 문구를 인용할 때도 그 용어를 쓴다.
- **기획서**: 결정과 그 이유를 적는 문서라 문장이 길어도 괜찮다. 그래도 1~3절의 서식·어휘 규칙은 같다.

## 6. 다 쓴 뒤 점검표

고친 파일에서 아래를 찾아본다 (Grep으로 `—`, `\*\*.*\*\* —`, `통해`, `수 있을 것`, `또한` 등).

- [ ] 줄표(—)와 "굵은 소제목 — 설명" 목록이 없다
- [ ] 굵은 글씨가 경고 한두 곳뿐이다
- [ ] 부풀린 말·상투구·번역투가 없다
- [ ] 대비 구문, 문두 접속사 연속, 끝맺음 요약이 없다
- [ ] 막연한 효과 대신 동작·조건이 적혀 있다
- [ ] 사실·수치·명령어가 원래와 같고 지금 코드와 맞다
- [ ] 소리 내어 읽었을 때 사람이 설명하는 말처럼 들린다
